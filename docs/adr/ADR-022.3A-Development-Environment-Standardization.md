# ADR-022.3A
## Development Environment Standardization

### 1. Context

PATCH-022.3 validation established that the complete test suite can pass when
the required test database configuration and test dependencies are present.
However, that successful environment cannot be reproduced reliably from the
governed repository state alone.

The current environment has unpinned dependencies, does not govern production,
development, and test dependencies as distinct responsibilities, and can depend
on package-index state, prior image state, or manual setup. The test database,
migration state, environment variables, and validation evidence also require a
consistent architectural contract.

SATCO therefore requires governed environment inputs rather than treating a
previous successful build or test execution as proof of reproducibility.

### 2. Decision

#### 2.1 Dependency Governance

The dependency graph shall have a single authoritative root.

All dependency declarations and resolutions shall originate from one governed
source. Dependency additions, removals, classifications, and version changes
shall be explicit and reviewable.

Manual installation, hidden environment state, and independently maintained
dependency graphs shall not become required inputs.

#### 2.2 Dependency Separation

Production, development, and test dependencies shall have distinct
responsibilities:

- Production dependencies are required to operate the SATCO Platform.
- Development dependencies support engineering and local development.
- Test dependencies support automated validation.

Development and test dependencies may extend the production dependency set.
Production environments shall not include development or test tooling unless it
is also an approved runtime requirement.

The physical dependency organization and supporting tooling shall be defined by
the approved operational standard and implementation PATCH.

#### 2.3 Version Pinning

Direct dependencies shall use governed versions.

Transitive dependency resolution shall be deterministic and reviewable. Floating
dependency baselines shall not define an approved environment.

Emergency security updates remain subject to governance and validation, even
when an expedited change process is required.

#### 2.4 Deterministic Docker Builds

Development Docker images shall be deterministic and reproducible solely from
the repository state and governed external base inputs.

Builds shall not depend on:

- A previously successful image.
- Local package caches as authoritative state.
- Manual container modifications.
- Undeclared host dependencies.
- Undocumented environment configuration.

Equivalent governed inputs shall produce functionally equivalent environments.

#### 2.5 Environment as Code

SATCO shall govern the development environment as architectural assets,
including:

- Docker configuration.
- The dependency graph.
- Environment-variable contracts.
- Alembic migration state.
- The test database contract.
- Validation entry conditions.

These assets shall be versioned, reviewed, and changed through the Docs-First
workflow.

#### 2.6 Dedicated Test Database

Automated database tests shall use a dedicated PostgreSQL test database.

Test execution shall not fall back to a development or production database. The
test environment shall verify database identity, connectivity, and expected
Alembic revision before database-backed validation begins.

Automated tests shall be idempotent. Repeated execution shall not corrupt or
invalidate the testing environment.

Destructive database actions remain subject to separate safety and operational
governance.

#### 2.7 Reproducible Validation

Validation shall be performed in an environment reconstructed from governed
inputs.

Validation evidence shall identify, at minimum:

- Git commit.
- Docker image.
- Alembic revision.
- Test database.
- Executed commands.
- Test results.

A passing result without sufficient environment identity is not complete
validation evidence.

#### 2.8 Environment Reproducibility

A clean repository state shall be sufficient to reconstruct the governed:

- Dependency resolution.
- Runtime environment.
- Service topology.
- Environment configuration.
- Migration state.
- Test execution behavior.

Undocumented local preparation shall not be required.

### 3. Consequences

#### Positive Consequences

- Development and validation environments become repeatable and auditable.
- Dependency drift and accidental production tooling are reduced.
- Test results can be associated with an exact environment state.
- Database-backed tests remain isolated from development and production data.
- Environment changes become visible architectural changes.

#### Trade-offs

- Dependency updates require explicit review and validation.
- Pinned resolution requires regular maintenance.
- Environment changes may require coordinated updates across governed assets.
- Clean-environment validation may take longer than reuse of uncontrolled local
  state.

#### Long-Term Architectural Impact

Environment configuration becomes part of SATCO architecture governance.
Future platform work inherits a stable dependency, Docker, database, and
validation contract.

#### Migration Impact

The current environment shall be migrated to the governed model through an
approved implementation PATCH. Existing behavior is not architectural authority
where it differs from this ADR.

Migration shall preserve product behavior while replacing undeclared or
non-deterministic environment inputs.

#### Future Extensibility

The decision permits future evolution of dependency tooling, container
construction, validation automation, and environment topology without changing
the governing principles.

Such changes shall preserve the single authoritative dependency root,
environment classification, deterministic construction, test isolation, and
validation traceability.

### 4. Alternatives Considered

#### 4.1 Continue with the Current Environment

This alternative would retain the environment that produced a successful test
run.

It was rejected because successful prior execution does not prove that the
environment can be reconstructed. Unpinned resolution, mixed dependency
responsibilities, and incomplete environment evidence remain uncontrolled.

#### 4.2 Separate Development Manually

This alternative would rely on developers to install and maintain development
and test tooling outside the governed environment.

It was rejected because manual separation creates hidden state, inconsistent
workstations, and validation results that cannot be traced to repository inputs.

#### 4.3 Environment Governance Through ADR

This alternative is selected.

It establishes durable principles before implementation, makes environment
state subject to Docs-First governance, and allows an operational standard and
implementation PATCH to define compliant realization without converting current
repository details into architectural authority.

### 5. Compliance Requirements

Every future PATCH affecting the development environment shall satisfy the
following rules:

1. The dependency graph shall have one authoritative governed root.
2. Production, development, and test dependencies shall have explicit
   responsibilities.
3. Production environments shall exclude development and test tooling unless it
   is an approved runtime requirement.
4. Direct dependency versions shall be governed.
5. Transitive dependency resolution shall be deterministic and reviewable.
6. Dependency changes shall be explicit, reviewed, and validated.
7. Development Docker images shall be reproducible from repository state and
   governed external base inputs.
8. Previous images, caches, manual container changes, and undeclared host
   packages shall not be required inputs.
9. Docker configuration shall be governed as Environment as Code.
10. Environment-variable contracts shall be explicit and governed.
11. Alembic shall remain the authority for relational schema migration state.
12. Automated database tests shall use the dedicated test database.
13. Tests shall not fall back to development or production databases.
14. Test database identity and migration state shall be verified before
    database-backed validation.
15. Automated tests shall be idempotent.
16. Validation shall be executed from governed environment inputs.
17. Validation evidence shall identify the Git commit, Docker image, Alembic
    revision, test database, executed commands, and test results.
18. Undocumented manual preparation shall not be required for a compliant
    environment.
19. Current implementation shall not be treated as architecture authority where
    it conflicts with approved governance.
20. Environment changes shall follow the SATCO Docs-First workflow.
