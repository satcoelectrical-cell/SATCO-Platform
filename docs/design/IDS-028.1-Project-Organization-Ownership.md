## 4. Migration Contract

### Revision

- revision: `e02810000001`;
- sole parent: `e02600000001`, the verified repository head at IDS creation;
- PostgreSQL transactional DDL is required;
- obtain a lock preventing concurrent insert/update of `projects` during
  expand/backfill/constrain validation.

If repository head changes before implementation, IRR must stop and this parent
must be re-reviewed. No merge revision may be improvised.

### Preconditions

The upgrade must assert:

- `projects`, `organizations`, `user_organization_memberships`, and `users`
  exist;
- when at least one Project requires backfill, the approved email resolves
  case-insensitively to exactly one User, that User is active with role exactly
  `admin`, and no duplicate/case-conflicting approved email exists;
- the default Organization UUID is either absent or identifies an active row;
- the Project table has not already reached a conflicting ownership shape.

Any failure raises and rolls back the whole revision.

### Preservation snapshot

Before mutation, capture transaction-local evidence for every Project:

- row count;
- ordered Project IDs;
- deterministic digest over every pre-existing Project column;
- referential-integrity state for tables referencing `projects.id`.

The seven known development Projects must be present in the inspected target.
If execution discovers a count other than seven in this named development
environment, stop for a new inventory decision. Clean and isolated test
databases use their own declared fixture expectations.

### Expand and bootstrap

1. add nullable UUID `projects.organization_id`;
2. add FK `fk_projects_organization_id_organizations` with `ON DELETE RESTRICT`;
3. insert the fixed Organization with `is_active = true` only when an unowned
   Project exists and the UUID is absent;
4. update only Projects where `organization_id IS NULL` to the fixed UUID;
5. when legacy Project backfill occurred, upsert exactly one membership for the
   approved admin and fixed Organization with `is_enabled = true`,
   `is_selected = true`;
6. before selection, clear `is_selected` only for other memberships belonging
   to that same approved admin, preserving their enabled state;
7. do not change the engineer's User or membership state; read only the minimum
   before/after values required to prove preservation.

Membership timestamps follow database defaults; on conflict, update only
`is_enabled`, `is_selected`, and `updated_at`. User identity, role, password,
active state, and timestamps remain untouched.

### Validate and constrain

Before NOT NULL:

- Project count and ordered IDs equal the snapshot;
- digest of all pre-existing Project columns equals the snapshot;
- every Project has the fixed Organization in the seven-Project development
  migration case;
- no null or dangling Organization FK exists;
- exactly one enabled selected membership exists for the approved admin and it
  points to the fixed active Organization;
- the engineer User row and any pre-existing engineer memberships are byte/value
  unchanged;
- all pre-existing Project references remain valid.

Then create `ix_projects_organization_id` and set
`projects.organization_id NOT NULL`. Retain global
`uq_projects_project_code` unchanged.

### Downgrade

Downgrade drops only `ix_projects_organization_id`, the Project Organization
FK, and the Project Organization column. It must not delete or modify Projects,
Users, Organization rows, or memberships. Forward repair is preferred after
the ownership boundary is used.

## 5. Domain and Persistence Contract

Add required `Project.organization_id` UUID with Organization FK and read-only
relationship if needed. Organization is supplied only by trusted application
context. It is excluded from Project create/update writable schemas and cannot
be changed after creation.

`ProjectRepository` methods `get_all`, `get_by_id`, `get_by_code`, `create`,
`update`, `delete`, and workspace-history validation must operate under an
explicit trusted Organization UUID. `_base_query` must require and filter it.
No protected path may call a global Project lookup.

Project Code allocation and global uniqueness remain unchanged.

## 6. API and Application Contract

Project and Search routers replace `get_current_user` with
`get_current_user_organization_context`. Services receive the authenticated
User plus trusted Organization UUID; clients supply neither ownership nor
selection.

Service order is:

1. resolve authenticated active Organization context;
2. query Project within that Organization;
3. return `PROJECT_NOT_FOUND` for absent/foreign Project;
4. apply existing owner/assignee/admin business authorization;
5. execute mutation without changing Organization.

Project API response shape remains backward compatible and need not disclose
`organization_id` in PATCH-028.1.

## 7. Search Contract

`search_projects` requires Organization UUID and filters before count,
pagination, and materialization. `search_workspaces` joins Project and applies
the same Organization filter before role/membership visibility. `search_all`
and `SearchService` require trusted Organization context for Project and
Workspace results.

Customer and Contact tenancy are not redesigned here. They must not become an
alternate route to Project or Workspace identity. Their current global behavior
is recorded as separate architecture debt and is not evidence of Project scope.

## 8. Dependent Loader Contract

Every authorized Workspace, Context, Context Relationship, Object,
Relationship, and Evidence helper that loads a Project must accept the actor's
trusted Organization UUID and filter by both Project ID and Organization ID.
For records carrying their own Organization UUID, validation additionally
requires equality with the Project.

Cross-Organization IDs result in existing protected-not-found behavior. No
foreign ID, title, count, owner, workspace, object, evidence, or relationship
detail may be disclosed.

## 9. Test Contract

Migration tests must cover:

- the representative seven-Project legacy snapshot, preserving all rows,
  values, IDs, and foreign references;
- approved admin membership created/enabled/selected when legacy backfill is
  required;
- engineer User and memberships unchanged;
- no new User rows;
- clean database without mandatory bootstrap User, and mixed
  already-owned/unowned rows;
- existing active default UUID and conflicting inactive UUID;
- missing, duplicate-case, inactive, or non-admin bootstrap user abort;
- pre-existing selected membership for admin is deselected safely;
- assertion failure rolls back every schema/data change;
- downgrade preserves Organization, memberships, Users, and Projects;
- upgrade/downgrade/upgrade.

Application tests must cover same-Organization CRUD/list/Search and
cross-Organization protected-not-found, counts, pagination, create derivation,
immutable transport fields, Workspace and all dependent loaders. Run focused
tests and the complete backend suite.
