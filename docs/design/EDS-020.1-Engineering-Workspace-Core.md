## Canonical Definition

Engineering Workspace is the digital operational environment where engineering
work is understood, planned, reviewed, explained, and continuously improved.

It is not a document repository.

It is not a task board.

It is not a project folder.

It is the engineer's operational home inside SATCO.

## Engineering Intent

Engineering Workspace Core gives discipline work a durable identity,
accountable ownership, controlled lifecycle, participation boundary, history,
and discoverability.

Without the Core, discipline work can only be inferred from Project metadata,
documents, conversations, or future features. Engineers would lose a stable
place from which SATCO can later assemble Engineering Context while preserving
who owns the work, who may contribute, what lifecycle state applies, and what
changed.

The Core reduces future engineering effort by preventing each later capability
from independently recreating Project/Discipline identity, authorization,
ownership, archival, audit, and navigation semantics.

## Primary User Story

As an authorized engineer, I can locate a Project's discipline Workspaces,
identify the Discipline and accountable people, understand the Workspace
lifecycle state, and enter the correct operational boundary without treating
the Workspace as a folder, task list, or AI conversation.

## Scope

PATCH-020.1 includes:

- Engineering Workspace identity;
- governed Discipline values;
- one immutable Workspace identity per Project and Discipline;
- Workspace lifecycle;
- accountable owner and optional primary assignee;
- minimum collaborator membership;
- create, list, retrieve, metadata update, transition, archive, and restore;

- PostgreSQL, service, API, permission, audit, search, and migration tests;

## Domain Model

### Engineering Workspace Aggregate

Engineering Workspace is a child aggregate of Project. It owns:

- immutable Project and Discipline identity;
- description metadata;
- lifecycle status and archival timestamp;
- accountable owner;
- optional primary assignee;
- collaborator membership;
- creator and timestamps;
- optimistic concurrency version.

It references Project and User records. It does not own or delete them.

### Engineering Workspace Member

Membership is a minimal association between one Workspace and one active
internal User. It means the User is an authorized collaborator or reviewer.

PATCH-020.1 does not persist a Workspace-specific member role. Accountable
owner and primary assignee remain explicit Workspace fields. Additional
Workspace role administration requires evidence and later approval.

## Field Definitions

### `engineering_workspaces`

| Field | Type concept | Required | Mutable | Rule |
|---|---|---:|---:|---|
| `id` | integer primary key | Yes | No | Internal identity consistent with current Project routes |
| `project_id` | integer foreign key | Yes | No | References `projects.id` with restrictive deletion |
| `discipline` | bounded string | Yes | No | Lowercase governed value |
| `description` | text | No | Yes | Trimmed; maximum 5,000 characters |
| `status` | bounded string | Yes | Via transition only | Defaults to `draft` |
| `owner_id` | integer foreign key | Yes | Yes | Active internal User |
| `primary_assignee_id` | integer foreign key | No | Yes | Active internal User |
| `created_by_id` | integer foreign key | Yes | No | Authenticated creator |
| `version` | positive integer | Yes | System only | Defaults to 1 and increments on each mutation |
| `archived_at` | timezone-aware timestamp | Conditional | Via archive/restore | Required exactly when status is `archived` |
| `created_at` | timezone-aware timestamp | Yes | No | Server-controlled |
| `updated_at` | timezone-aware timestamp | Yes | System only | Changes on each mutation |

No persisted `name` field is included.

The Workspace display name is system-derived from the governed Discipline,
using the form `<Discipline label> Engineering Workspace`. This avoids a
second editable identity competing with Discipline. A future justified display
alias would be metadata, not identity, and requires separate scope.

### `engineering_workspace_members`

| Field | Type concept | Required | Mutable | Rule |
|---|---|---:|---:|---|
| `workspace_id` | integer foreign key | Yes | No | Part of composite primary key |
| `user_id` | integer foreign key | Yes | No | Part of composite primary key |
| `added_by_id` | integer foreign key | Yes | No | Active authenticated actor at creation |
| `created_at` | timezone-aware timestamp | Yes | No | Server-controlled |

The composite primary key prevents duplicate membership.

## Discipline Decision

### Chosen Approach

Use one canonical Python `Discipline` string enum for application and OpenAPI
validation, backed by a named PostgreSQL check constraint on a `VARCHAR(32)`
column.

Initial values:

- `electrical`
- `instrumentation`
- `control`
- `mechanical`
- `civil`
- `process`

This is the governed-string-with-database-constraint approach.

### Rationale

- It gives Pydantic and OpenAPI an explicit enum.
- PostgreSQL rejects invalid values independently of the application.
- Search remains simple and indexable.
- A future additive migration can extend values without PostgreSQL enum
  replacement mechanics.
- It avoids a lookup table and administration capability before such
  administration exists.
- It is compatible with the repository's current string-enum pattern.

Free text is rejected. A PostgreSQL native enum is rejected because value
evolution and downgrade are less flexible. A lookup table is deferred until
administration, metadata, localization, or customer-specific governance is a
demonstrated requirement.

## Uniqueness Decision

There is exactly one Workspace identity per Project and Discipline for all
time, including while archived.

A named unique constraint on `(project_id, discipline)` enforces this rule.
Archived Workspaces cannot be replaced by a new record. They may only be
restored through the governed restore operation.

This preserves unambiguous identity and history and prevents two competing
discipline homes. A partial unique index on active rows is rejected because it
would allow historical replacement and ambiguous restoration.

## Status Lifecycle

Accepted statuses:

| Status | Meaning |
|---|---|
| `draft` | Identity, ownership, and minimum metadata are being established |
| `active` | The Workspace is available for current discipline engineering |
| `on_hold` | Engineering work is intentionally paused |
| `under_review` | The Workspace as a whole is being assessed at a stage boundary |
| `completed` | Recorded Workspace scope has met its completion conditions |
| `archived` | The Workspace is retained as non-operational history |

Workspace Status is not Project Status, Workspace Readiness, Engineering
Health, Human Review, or deliverable approval.

Permitted transitions:

```text
draft -> active
draft -> archived
active -> on_hold
active -> under_review
active -> archived
on_hold -> active
on_hold -> archived
under_review -> active
under_review -> completed
under_review -> archived
completed -> active
completed -> archived
archived -> active
```

Self-transitions are idempotent only when the submitted version still matches
and no other metadata changes. Unsupported transitions return a domain
validation error.

Completion requires the Workspace to pass through `under_review`. Reopening or
restoring requires a non-empty reason. Archiving from any permitted state also
requires a reason.

`archived` is the lifecycle status. `archived_at` is its historical timestamp,
not a second independent state. The database enforces:

```text
status = 'archived' if and only if archived_at is not null
```

## Ownership and Membership

### Owner

The owner is accountable for Workspace governance, lifecycle coordination,
assignment, and review readiness. Ownership does not imply sole technical or
formal approval authority.

### Primary Assignee

The primary assignee is the engineer currently carrying primary responsibility
for discipline work. The field is optional so a Draft Workspace may exist
before assignment.

### Collaborator

A collaborator is an active internal User explicitly associated with the
Workspace for contribution or review.

Owner and primary assignee receive access through their explicit fields and do
not need duplicate membership rows. If either also appears in membership, the
service treats the request as redundant and rejects it to keep semantics clear.

Removing a collaborator does not erase audit history. Inactive Users cannot be
newly assigned or added. Existing relationships remain visible if a User later
becomes inactive, but that User cannot mutate the Workspace.

## Permission Matrix

The implementation persists only current roles: `admin` and `engineer`.

| Capability | Admin | Engineer |
|---|---|---|
| Create Workspace | Any Project | Only a Project they own |
| List Project Workspaces | Any Project | Project owner/assignee or Workspace participant |
| Retrieve Workspace | Any | Project owner/assignee or Workspace participant |
| Update description | Any | Project owner, Workspace owner, or primary assignee |
| Assign owner | Any | Project owner only |
| Assign primary assignee | Any | Project owner or Workspace owner |
| Add/remove collaborator | Any | Project owner or Workspace owner |
| Change lifecycle status | Any | Project owner or Workspace owner |
| Archive | Any | Project owner or Workspace owner |
| Restore | Any | Project owner or Workspace owner |
| Search Workspaces | Any | Only Workspaces the engineer may retrieve |

Workspace participant means Workspace owner, primary assignee, or collaborator.
Project primary assignee may list/retrieve the Project's Workspaces but does
not automatically gain mutation rights.

Future Engineering Manager, Project Manager, Lead Engineer, Reviewer, and
Viewer personas map conceptually to capabilities. They are not new persisted
roles in PATCH-020.1.

Authorization must be enforced in service and repository query boundaries.
Unauthorized Workspace identifiers return `404` where disclosure would leak
cross-Project existence; authenticated attempts against a visible Workspace
without mutation rights return `403`.

## Project Relationship

- Workspace creation is explicit and never automatic.
- Project creation does not generate Workspaces.
- Project owner and primary assignee are not copied into Workspace fields
  silently.
- Creator chooses an owner explicitly; omission defaults to the creator only
  when the creator is eligible.
- Workspaces cannot be created for `completed` or `cancelled` Projects.
- A Workspace cannot be activated or restored while its Project is
  `completed` or `cancelled`.
- Project `on_hold` does not silently change Workspace statuses; the Project
  condition remains visible to later UI and mutations that would conflict are
  rejected.
- Existing Project status changes do not cascade Workspace transitions.
- Physical Project deletion is blocked once any Workspace record exists,
  including archived history.
- Existing deletion behavior remains unchanged for Projects without
  Workspaces.

The Project deletion guard is the only approved change to existing Project
behavior and is required by ADR-014 historical-preservation rules.

## Archival Model

Archival is explicit and non-destructive.

- No ordinary physical-delete endpoint exists.
- Archive changes status to `archived`, records `archived_at`, increments
  version, and emits audit history.
- Restore changes `archived` to `active`, clears `archived_at`, increments
  version, and requires a reason.
- Archived rows, memberships, and audit records remain intact.
- Normal Project Workspace lists exclude archived rows by default.
- `include_archived=true` requires the same authorization and exposes them.
- Direct Workspace retrieval can return an archived Workspace to an authorized
  user with its archived state visible.
- Universal Search excludes archived Workspaces by default.
- A future explicit archived-search filter may be added without changing the
  identity model.

Foreign keys use restrictive deletion for Project and owner/creator history.
Membership deletion removes current access association but does not remove
audit evidence.

## Concurrency Model

Use integer optimistic concurrency.

- `version` starts at 1.
- Every metadata, assignment, membership, transition, archive, or restore
  mutation submits `expected_version`.
- Repository updates include `WHERE id = :id AND version =
  :expected_version`.
- A successful mutation increments `version` by one.
- Zero updated rows produce `WorkspaceVersionConflict`.
- Responses return the current version.

This is clearer and safer than timestamp comparison and less complex than
holding row locks across HTTP requests. PostgreSQL row-level behavior may be
used inside a short transaction, but pessimistic locking is not the public
concurrency contract.

Membership changes increment the parent Workspace version so concurrent
assignment and access changes cannot silently overwrite one another.

## Audit Contract

Required action values:

- `workspace_created`
- `workspace_updated`
- `workspace_owner_changed`
- `workspace_primary_assignee_changed`
- `workspace_collaborator_added`
- `workspace_collaborator_removed`
- `workspace_status_changed`
- `workspace_archived`
- `workspace_restored`

Each audit event records:

- actor through `user_id`;
- entity `ENGINEERING_WORKSPACE`;
- Workspace identifier;
- Project identifier in details;
- action;
- before and after state relevant to the action;
- timestamp through Audit Log creation;
- reason for archive, restore, reopening, and other material transitions;
- resulting Workspace version.

PATCH-020.1 reuses the existing Audit Service and Audit Log schema. It does not
redesign universal audit.

Domain mutation and required audit creation must behave as one service
operation. Because the current repository and Audit Service commit
independently, implementation must introduce bounded transaction control for
Workspace operations without changing unrelated audit consumers.

Sensitive or unnecessary User data must not be copied into audit details.

## Search Contract

PATCH-020.1 extends Universal Search with a `workspaces` result collection and
a `workspace` search type.

Searchable values are limited to:

- derived Workspace display name;
- Discipline;
- Project name;
- exact or partial Project Code;
- Workspace Status;
- owner username or full name;
- primary-assignee username or full name.

Results include only Workspaces the current User may retrieve. Archived
Workspaces are excluded. Search repository queries perform authorization
filtering before pagination and count calculation.

Search relevance is discovery only and must not be presented as engineering
priority. PATCH-020.1 does not add a separate search subsystem.

## API Contract

### Endpoints

| Method and path | Purpose | Success |
|---|---|---:|
| `POST /projects/{project_id}/workspaces` | Create a Draft Workspace | `201` |
| `GET /projects/{project_id}/workspaces` | List visible Project Workspaces | `200` |
| `GET /workspaces/{workspace_id}` | Retrieve one visible Workspace | `200` |
| `PATCH /workspaces/{workspace_id}` | Update description or assignments | `200` |
| `POST /workspaces/{workspace_id}/transitions` | Apply a lifecycle transition | `200` |
| `POST /workspaces/{workspace_id}/archive` | Archive with reason | `200` |
| `POST /workspaces/{workspace_id}/restore` | Restore with reason | `200` |
| `POST /workspaces/{workspace_id}/collaborators` | Add a collaborator | `200` |
| `DELETE /workspaces/{workspace_id}/collaborators/{user_id}` | Remove membership only | `204` |

The collaborator `DELETE` removes an access association, not governed
Workspace history. There is no Workspace `DELETE`.

### List Contract

Project Workspace listing supports:

- `page`, default 1 and minimum 1;
- `size`, default 20 and range 1–100;
- optional Discipline;
- optional Workspace Status;
- optional owner;
- optional primary assignee;
- `include_archived`, default false;
- allow-listed sorting by Discipline, status, created time, or updated time;
- deterministic `id` tie-breaking.

### Authorization and Validation

All endpoints require JWT access authentication. Services validate:

- Project visibility and lifecycle;
- Discipline;
- uniqueness;
- active internal Users;
- mutation capability;
- lifecycle transition;
- archive/restore reason;
- expected version;
- membership redundancy.

### Idempotency

- List and retrieve are naturally idempotent.
- Repeating creation for the same Project/Discipline returns the existing
  conflict; it does not create a duplicate.
- A self-transition with the current version is a no-op response.
- Repeating archive or restore after state changed returns a state conflict.
- Adding an existing collaborator returns a conflict.
- Removing absent membership returns `404`.

An idempotency-key subsystem is not justified for PATCH-020.1.

## Schema Design

Future Pydantic schemas:

### `EngineeringWorkspaceCreate`

- `discipline`: required `Discipline`;
- `description`: optional, trimmed, maximum 5,000 characters;
- `owner_id`: optional positive integer;
- `primary_assignee_id`: optional positive integer;
- `collaborator_ids`: optional unique list of positive integers, bounded to
  100 entries.

Status is not accepted at creation; it is always `draft`.

### `EngineeringWorkspaceUpdate`

- `description`;
- `owner_id`;
- `primary_assignee_id`;
- `expected_version`: required positive integer.

Discipline, Project, creator, status, and archival state are not metadata
updates.

### `WorkspaceStatusTransitionRequest`

- `status`: required target `WorkspaceStatus`;
- `reason`: optional generally, required for completion reopening;
- `expected_version`: required.

Archive and restore are rejected through this generic schema so their explicit
endpoints preserve intent.

### `WorkspaceArchiveRequest`

- `reason`: required, trimmed, 1–2,000 characters;
- `expected_version`: required.

### `WorkspaceRestoreRequest`

- `reason`: required, trimmed, 1–2,000 characters;
- `expected_version`: required.

### Membership Schemas

`EngineeringWorkspaceCollaboratorAdd` contains `user_id` and
`expected_version`. Removal receives `expected_version` as a required query
parameter because a DELETE body is avoided.

### Response Schemas

`EngineeringWorkspaceResponse` includes all UI contract fields, nested short
User summaries, collaborator summaries, version, and `allowed_actions`.

`EngineeringWorkspaceListResponse` uses the existing generic paginated shape:
`items`, `total`, `page`, and `size`.

All request schemas forbid extra fields. Examples use advisory-neutral,
engineering-specific language and do not imply future capabilities.

## Database Design

### `engineering_workspaces`

Conceptual constraints:

- named primary key on `id`;
- named foreign keys to Project, owner User, primary-assignee User, and creator
  User;
- named unique constraint on `(project_id, discipline)`;
- named check for Discipline values;
- named check for Workspace Status values;
- named check for `version >= 1`;
- named check coupling `status` and `archived_at`;
- non-null Project, Discipline, status, owner, creator, version, and
  timestamps.

Conceptual indexes:

- `(project_id, status)`;
- `(project_id, discipline)` through the unique constraint;
- `owner_id`;
- `primary_assignee_id`;
- `status`;
- `updated_at`;
- optional PostgreSQL text-search support is not required for the MVP query
  volume.

### `engineering_workspace_members`

Conceptual constraints and indexes:

- composite primary key `(workspace_id, user_id)`;
- restrictive foreign key to Workspace;
- restrictive foreign keys to member User and adding User;
- index on `user_id`;
- index on `added_by_id`.

Core identity and lifecycle data must not be stored in JSON.

## Repository Responsibilities

The Workspace repository owns:

- Project-scoped and authorization-filtered retrieval;
- paginated listing and archived filtering;
- persisted uniqueness checks for helpful errors;
- atomic version-checked updates;
- membership persistence;
- active User retrieval support;
- existence checks used by the Project deletion guard;
- deterministic filters and allow-listed sorting.

Database constraints remain authoritative under concurrency. The repository
does not decide permissions, transitions, or audit meaning.

Search repository owns Workspace discovery queries and authorization filtering.

## Service Responsibilities

The Workspace service owns:

- Project and User relationship validation;
- current-role capability decisions;
- Project and Workspace scope enforcement;
- display-name derivation;
- uniqueness orchestration;
- lifecycle and Project-state rules;
- owner, assignment, and membership semantics;
- optimistic concurrency orchestration;
- archive and restore behavior;
- audit snapshots and reasons;
- mapping persistence conflicts to domain errors;
- bounded transaction completion.

The Project service invokes the repository history check before physical
Project deletion.

## Router Responsibilities

Routers own:

- paths and HTTP methods;
- authentication dependencies;
- typed query and body validation;
- response models and status codes;
- OpenAPI examples;
- dependency injection;
- mapping already-classified domain outcomes through centralized handlers.

Routers contain no authorization, lifecycle, persistence, or audit logic.

## Migration Strategy

Create one additive Alembic revision based on current head
`f18a1c0e2026`.

Upgrade:

1. create `engineering_workspaces`;
2. create explicit constraints and indexes;
3. create `engineering_workspace_members`;
4. create explicit constraints and indexes;
5. verify foreign keys, check constraints, nullability, and uniqueness through
   isolated PostgreSQL tests.

The migration:

- does not alter or backfill existing Project rows;
- does not create speculative Workspaces;
- works through the full fresh migration chain;
- works on a compatible database already at `f18a1c0e2026`;
- uses deterministic, explicitly named objects;
- remains the sole schema-creation authority.

Downgrade drops the membership table first and Workspace table second,
including their indexes and constraints. Downgrade destroys PATCH-020.1 data
and is permitted only in isolated validation or under separately approved
operational rollback. Production rollback should normally restore the prior
application while retaining the additive tables.

No migration creation or execution is authorized by this specification.

## Compatibility

- Existing Project integer IDs and Project Codes remain unchanged.
- Existing Customer, owner, and primary-assignee behavior remains unchanged.
- Current Project lifecycle, progress, and APIs remain unchanged except
  Project deletion is blocked after Workspace history exists.
- Current `admin` and `engineer` roles remain the only persisted roles.
- Existing Project and CRM search results remain compatible.
- Universal Search gains an additive Workspace collection/type.
- Existing audit storage and access remain unchanged.
- PostgreSQL remains the structured source of truth.
- Alembic remains the exclusive schema authority.
- Application startup remains schema read-only.

## Alternatives

Considered approaches included:

- free-text, native database enum, lookup-table, and governed-string
  Disciplines;
- editable Workspace names versus derived display names;
- permanent uniqueness versus active-row partial uniqueness;
- archive flag versus lifecycle status;
- timestamp versus integer optimistic concurrency;
- implicit Project membership versus explicit minimal membership;
- generic DELETE versus explicit archive.

The chosen approaches minimize identity ambiguity and premature
administration while retaining database enforcement and future evolution.

## Rejected Designs

- free-text Discipline;
- PostgreSQL native Discipline enum;
- editable name as a competing identity;
- multiple or nested Workspaces;
- automatic default Workspace generation;
- replacement of archived Workspace identity;
- hard-delete Workspace API;
- archive flag independent of lifecycle;
- unversioned conflicting updates;
- complex Workspace-specific member roles;
- new global RBAC roles;
- separate search subsystem;
- business logic in routers;
- JSON storage for core identity or lifecycle;
- implementation of later PATCH-020 concepts.

| Risk | Control |
|---|---|
| Cross-Project information leakage | Authorization-filter repository queries and negative tests |
| Project deletion destroys history | Restrictive foreign key and service conflict guard |
| Status/readiness confusion | Core exposes Workspace Status only |
| Discipline expansion requires migration | Explicit additive migration and enum update |
| Current RBAC is coarse | Ownership, assignment, and membership scope current roles |
| Audit and mutation commits diverge | Bounded Workspace transaction orchestration |
| Stale concurrent updates | Required integer version |
| Archived identity duplication | Permanent Project/Discipline uniqueness |
| Membership complexity expands | No member-role field in PATCH-020.1 |
| Search changes response assumptions | Additive typed collection with regression tests |
| Scope drifts toward Cockpit or AI | Explicit exclusions and file-level review |

## Rollback

Before implementation, rollback is deletion of the two unapproved design
documents and restoration of ADR-014's prior status only under explicit
governance direction.

After implementation:

- application rollback keeps additive Workspace tables intact;
- migration downgrade is tested only in isolation and requires approval;
- no automatic Workspace backfill needs reversal;
- Project behavior returns to its prior form only if no Workspace history
  would become destructively exposed;
- created engineering history must not be silently discarded.

## Acceptance Criteria

1. One Workspace identity exists at most once per Project and Discipline.
2. Discipline is governed consistently in Python, Pydantic, OpenAPI, and
   PostgreSQL.
3. Display name does not compete with Discipline identity.
4. Status transitions are explicit and distinct from future readiness,
   health, and review.
5. Owner, primary assignee, and collaborator semantics are distinct.
6. Current-role permissions prevent cross-Project leakage.
7. Archive and restore preserve one historical identity.
8. Physical Workspace deletion is unavailable.
9. Project deletion cannot destroy Workspace history.
10. Conflicting updates return a version conflict.
11. Every successful material mutation produces the required audit evidence.
12. Universal Search discovers only authorized, operational Workspaces.
13. Existing Project Code search behavior remains unchanged.
14. OpenAPI documents every material success and failure contract.
15. A fresh PostgreSQL database reaches the new head entirely through Alembic.
16. An existing compatible database upgrades without Project mutation.
17. The complete PostgreSQL regression suite passes.
18. No later PATCH-020 capability is represented as implemented.
