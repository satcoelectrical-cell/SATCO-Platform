# EDS-028.1 — Project Organization Ownership

## 1. Document Control

This EDS defines a non-destructive transition from legacy Projects to explicit
Organization ownership. It does not authorize implementation or execution
against any database.

## 2. Accepted Data Decision

The Repository/Data Owner has classified all seven existing Projects as
development data that must be preserved. No reset, cleanup, deletion,
recreation, identifier replacement, or lossy transformation is permitted.

Because the inspected environment contains no Organization identity from which
ownership can be evidenced, the seven Projects shall be assigned to one
migration-owned default Organization created specifically for the legacy
development baseline.

This is an explicit Human ownership decision, not inferred ownership. The
migration shall record a stable Organization UUID and a stable bootstrap key in
source-controlled implementation constants. The Organization model currently
has no display name or key; PATCH-028.1 shall not expand it merely to label this
bootstrap row.

## 3. Invariants

After upgrade:

- every Project has exactly one non-null `organization_id`;
- `projects.organization_id` references `organizations.id` with `RESTRICT`;
- Project identity, Project Code, attributes, timestamps, and all existing
  foreign-key relationships remain unchanged;
- Organization is derived from authenticated PATCH-025 context on creation;
- transport input cannot set or mutate trusted Project Organization;
- Project transfer is unsupported;
- Project reads, lists, mutations, Search, and dependent lookups are scoped by
  trusted Organization before Project-level authorization;
- foreign-Organization Project IDs receive protected-not-found behavior;
- child records that carry Organization must equal their Project's
  Organization.

## 4. Migration Design

### 4.1 Preconditions

The revision shall be based on the repository migration head selected at IDS
and shall verify that PATCH-025 Organization tables and `projects` exist. The
deployment runbook shall capture before-state counts and immutable Project IDs.
The current development database at `d8271b8f1a29` must first traverse the
normal reviewed Alembic lineage; no alternate reset path is allowed.

### 4.2 Expand

Add `projects.organization_id` as nullable UUID. Add the foreign key only after
the referenced Organization table exists. Do not modify any other Project
column, key, sequence, or relationship.

### 4.3 Conditional bootstrap

If and only if at least one Project has null `organization_id`, insert the
approved default Organization by its fixed UUID when that UUID does not already
exist. If the UUID exists, it must be an active Organization; otherwise abort.
The insert must be idempotent and must not select an arbitrary existing
Organization.

The migration does not invent user membership. Organization selection and
membership bootstrap are operational access concerns and require a separately
approved mechanism. Lack of membership must not be solved by changing Project
ownership or deleting Projects.

### 4.4 Backfill

Update only rows where `projects.organization_id IS NULL`, assigning the fixed
default Organization UUID. This preserves all seven legacy rows in place and
also safely handles any additional legacy unowned rows discovered at execution.
Already-owned rows, if any, remain untouched.

### 4.5 Validate and constrain

Before enforcing the final constraint, the migration shall assert:

- Project count is unchanged;
- no Project ID disappeared or changed;
- zero Projects have null Organization;
- every Project Organization resolves to exactly one Organization;
- the seven recorded legacy Project IDs still exist;
- existing Project foreign-key dependants remain valid.

Any failed assertion aborts the transaction. Then create a non-unique index on
`organization_id` and alter the column to NOT NULL. Existing global Project
Code uniqueness remains unchanged; changing it to Organization scope is out of
scope.

### 4.6 Transaction and failure behavior

The schema expansion, conditional bootstrap, backfill, validation, and final
constraint shall run in one transactional Alembic upgrade where supported by
PostgreSQL. Failure rolls back the entire revision. No partial mapping may be
accepted.

### 4.7 Downgrade and forward repair

Downgrade is intentionally non-destructive: it may remove the Project
Organization index, foreign key, and column, but shall not delete Projects,
dependent records, or the bootstrap Organization. Retaining the Organization
avoids deleting identity or future memberships created after upgrade.
Operational environments should prefer forward repair over downgrade once
Project ownership becomes authoritative.

## 5. Application Design

### Project aggregate and schemas

`Project.organization_id` is required and immutable. Create request schemas do
not expose it as writable input. Responses may expose it only if current API
disclosure policy explicitly approves that field; tenant safety must not depend
on hiding it.

### Repository and service

Every Project repository operation accepts trusted `organization_id` and
filters by `(organization_id, project_id)` or Organization-scoped collection.
Unscoped `Session.get(Project, id)` and global Project queries are forbidden in
protected paths. Creation receives Organization from
`get_current_user_organization_context`. Update and delete never alter it.

Existing Project roles and business authorization remain in force after the
Organization filter. Organization membership alone does not grant Project
permission.

### Search

Project and Workspace Search queries join/filter through
`Project.organization_id == active_organization_id`. Counts and pagination are
computed after scope filtering so foreign tenant existence is not disclosed.

### Dependent domains

All Project-loading helpers in Workspace, Engineering Context, Engineering
Object, Relationship, Evidence, and future Capture paths must use trusted
Organization scope. When a dependent row also stores `organization_id`, create
and reference validation require equality with its Project. Existing dependent
rows are preserved; the migration does not rewrite their IDs or content.

## 6. Access Bootstrap Boundary

Mapping Projects to the default Organization does not by itself make that
Organization selectable by a User. Before application acceptance testing, a
Human-approved active user must have exactly one enabled selected membership in
the default Organization, using a separate bounded seed/administrative action
or an explicitly authorized migration step. The selected user must not be
guessed from Project owner, assignee, Customer, or row creation history.

This is a deployment readiness blocker, not a data-preservation blocker.

## 7. Audit and Verification

Required evidence:

- before/after Project count and ordered ID digest;
- before/after values for all pre-existing Project columns;
- foreign-key integrity checks;
- fixed bootstrap Organization UUID and decision reference;
- zero null or dangling ownership values;
- tests for clean database, seven-row legacy database, mixed already-owned and
  unowned data, idempotent UUID presence, inactive/conflicting bootstrap UUID,
  and forced validation failure rollback;
- cross-Organization Project CRUD, list, Search, Workspace, dependent-reference,
  count, and protected-not-found tests;
- complete backend regression and Alembic upgrade/downgrade/upgrade evidence.

Production or shared-environment execution requires an explicit backup,
restore test, maintenance plan, and Human go/no-go outside this EDS.

## 8. Scope Boundaries

No Organization administration UI/API, Project transfer, Customer redesign,
role redesign, frontend work, Capture persistence, destructive cleanup, or
Project Code uniqueness change is authorized.
