# IDS-020.2.2: Context Relationships and Interface Commitments

## Status

Accepted

## Purpose

This Implementation Design Specification defines the bounded implementation
contract for PATCH-020.2.2, the second Engineering Context Foundation
sub-patch.

It translates the accepted relationship and Interface Commitment architecture
in ADR-015 and EDS-020.2 into observable requirements without selecting a
technology, persistence representation, API, migration structure, repository,
service, or user interface.

PATCH-020.2.2 exists so SATCO can express explicit engineering dependencies
between authorized Project and Workspace Context without copying shared facts,
silently transferring authority, or turning Context into workflow management.
It establishes accountable information delivery while keeping provider
delivery, consumer review, and engineering acceptance distinct.

This document creates no implementation authority. Implementation remains
prohibited until this IDS is approved, an implementation plan is approved, and
an Implementation Readiness Review returns **Ready for Implementation**.

## Scope

PATCH-020.2.2 is limited to the minimum governed relationship and Interface
Commitment foundation required by accepted EDS-020.2.

It includes:

- explicit identity for each governed Context relationship;
- explicit direction where engineering meaning requires a source and target;
- an allow-listed initial relationship taxonomy;
- governing Project scope and optional provider and consumer Workspace scope;
- references to existing Context elements and native Project, Workspace,
  Discipline, User, and external-source identities;
- relationship purpose, applicability, and bounded engineering meaning;
- relationship owner or steward responsibility where applicable;
- relationship lifecycle and withdrawal without physical erasure;
- positive optimistic-concurrency version compatibility;
- explicit authority boundaries for relationship creation and change;
- Interface Commitment identity;
- provider and consumer accountability;
- required-information meaning and semantic completeness expectations;
- source and revision expectations without copying source content;
- bounded stage or due condition without schedule execution;
- recorded criticality supplied through an authorized process, without a
  criticality-assessment engine;
- Interface Commitment lifecycle;
- explicit change-impact and reassessment-needed standing;
- relationship and commitment audit hooks;
- least-privilege Project and cross-Workspace authorization;
- compatibility with PATCH-020.1 Workspace Core;
- compatibility with PATCH-020.2.1 Core Context identity, source,
  responsibility, authority, lifecycle, audit, and concurrency foundations.

### Initial relationship boundary

The initial implementation contract may represent only relationship meanings
needed for this patch:

- **requires:** an authorized Context element or consuming Workspace requires
  identified information for a stated use;
- **provided by:** an Interface Commitment identifies its accountable provider;
- **consumed by:** an Interface Commitment identifies its consuming Workspace;
- **potentially affects:** an explicitly recorded change-impact relationship
  identifies Context or a commitment that requires reassessment.

PATCH-020.2.1 subject and source references continue to express **applies to**
and **evidenced by** meaning. PATCH-020.2.2 must reference those foundations
without duplicating or replacing them.

No other EDS-020.2 relationship meaning is authorized in this patch.

### Information-delivery boundary

The Interface Commitment foundation is limited to accountable information
delivery:

- a provider acknowledges responsibility to supply defined information;
- the provider may record that bounded information and its source revision were
  provided;
- the consumer may record rejection, dispute, or that consumer review is
  required;
- fulfilment is bounded to stated use, supplied source, and supplied revision;
- provider delivery never records consumer engineering approval;
- where accepted EDS-020.2 requires Human Review for fulfilment, this patch may
  preserve the requirement and prevent premature fulfilment, but it does not
  implement the Human Review capability.

### Resolved assumptions

- Every governed relationship belongs to exactly one Project.
- Cross-Workspace does not mean cross-Project.
- A consuming Workspace is always a native Workspace in the governing Project.
- A provider may be an authorized Project participant, a Workspace in the
  governing Project, or a bounded external source reference.
- A provider or consumer reference does not transfer ownership of the native
  participant, Workspace, Context, or source.
- Interface Commitment is an engineering information contract, not a work
  order.
- Existing roles are sufficient for the foundation; capability derives from
  scope, participation, explicit responsibility, and source access.
- Administrator access is administrative and does not prove engineering
  competence.
- Provider delivery and consumer review are separate actions and authorities.
- Criticality may be recorded only as an explicit governed standing supplied
  to the commitment; this patch does not calculate it.
- Change impact is explicit and human-recorded; this patch does not infer
  impact.

## Required Domain Objects

The names in this section define domain responsibilities, not storage objects
or technology-specific representations.

### Governed Context Relationship

A durable, explicit statement that connects authorized Context or native scope
references through one allow-listed engineering meaning.

It requires:

- stable identity;
- one governing Project;
- allow-listed relationship meaning;
- explicit source side and target side;
- direction where required by the relationship meaning;
- stated purpose or applicability;
- accountable creator;
- accountable steward where continued maintenance is required;
- lifecycle standing;
- positive version;
- creation and last-change traceability.

A relationship is not inferred from proximity, matching text, shared tags,
common ownership, common Workspace membership, or AI output.

### Relationship Endpoint

One side of a governed relationship.

An endpoint:

- references an existing Context element, Project, Workspace, Discipline, or
  bounded external-source identity allowed by the relationship meaning;
- retains the native identity and governing scope of the referenced object;
- has an explicit semantic role such as requirement, required information,
  provider, consumer, or affected Context;
- does not copy native object state;
- does not gain ownership, authority, maturity, approval, or source access
  through the relationship.

Both endpoints must be valid within the governing Project boundary.

### Relationship Identity

The stable identity of one relationship statement.

Identity remains stable through authorized lifecycle and metadata changes. Two
relationships must not silently collapse merely because their endpoints are
the same. Distinct engineering meaning, direction, purpose, or applicability
may require distinct identities.

An implementation must reject accidental duplicate active relationships with
the same governing Project, relationship meaning, direction, endpoints, and
bounded purpose.

### Relationship Meaning

The allow-listed engineering semantics of the connection.

The initial meanings are:

- requires;
- provided by;
- consumed by;
- potentially affects.

Meaning must be explicit. A generic custom relationship label or arbitrary
relationship payload is not permitted.

### Relationship Responsibility

Explicit accountability for maintaining the relationship’s accuracy and
current-use standing.

It may include:

- relationship creator;
- information owner where relevant;
- engineering steward;
- Interface Commitment provider responsibility;
- consuming Workspace responsibility;
- designated reviewer reference for future review integration.

Responsibility identifies accountability, not competence or authority over
either endpoint.

### Relationship Lifecycle

The minimum lifecycle required to distinguish a relationship available for
current engineering use from one withdrawn from current use.

Initial standing:

- **Current**
- **Withdrawn**

Withdrawal:

- preserves identity and audit evidence;
- requires explicit authorization and reason;
- does not delete either endpoint;
- does not withdraw the linked Context;
- does not complete, reject, dispute, or supersede an Interface Commitment;
- prevents normal current-use reliance on the relationship.

Restoration returns the same identity to current use through an authorized,
reasoned, version-protected action.

### Interface Commitment

A governed information-delivery dependency in which an accountable provider
must provide defined information needed by one consuming Workspace.

It requires:

- stable identity;
- one governing Project;
- one provider;
- one consuming Workspace;
- explicit required information;
- stated intended use;
- semantic completeness expectations;
- expected source or evidence basis;
- stage or due condition;
- recorded criticality standing;
- steward;
- consumer review responsibility;
- confidentiality standing;
- lifecycle state;
- supplied source and revision where information has been provided;
- explicit reassessment-needed standing and reason where applicable;
- positive version;
- creation and change traceability.

The commitment references Context and sources without copying their meaning or
content.

### Commitment Provider

The accountable origin of required information.

The provider may be:

- an authorized Project participant;
- a Workspace in the governing Project;
- a bounded external source reference.

Provider responsibility is limited to the stated information and commitment.
It does not confer authority over the consuming Workspace’s interpretation,
review, design, or approval.

### Commitment Consumer

The native Workspace that requires the information for a stated use.

Consumer participation permits only the commitment actions authorized for the
consumer scope. It does not grant unrestricted traversal into provider
Workspace Context or restricted source meaning.

The consuming Workspace remains responsible for its engineering interpretation
and may not alter provider-owned source meaning.

### Required Information Definition

The bounded semantic contract for what must be provided.

It identifies:

- the engineering subject;
- required meaning;
- required qualifications such as unit, basis, condition, applicability, or
  revision where material;
- semantic completeness expectations;
- intended consumer use;
- expected source or evidence standing.

It must be precise enough to distinguish suitable information from an
unrelated document or unqualified value. It is not a task description or
document-content blob.

### Stage or Due Condition

An explicit engineering condition by which information is needed.

It may express a named Project stage, consumer-use condition, or externally
governed due reference. It does not create a schedule, timer, reminder,
notification, task, or automatic escalation.

### Commitment Lifecycle

The initial lifecycle states are:

- **Identified**
- **Acknowledged by Provider**
- **Information Provided**
- **Consumer Review Required**
- **Fulfilled for Stated Use**
- **Rejected**
- **Disputed**
- **Superseded**

Each state has one meaning:

- **Identified:** the information dependency and accountable parties are
  explicitly recorded.
- **Acknowledged by Provider:** the provider has acknowledged responsibility;
  completeness is not asserted.
- **Information Provided:** identified information, source, and revision have
  been supplied; consumer acceptance is not asserted.
- **Consumer Review Required:** supplied information requires consumer-side
  evaluation before reliance.
- **Fulfilled for Stated Use:** the commitment is satisfied only for its stated
  use, supplied source, and supplied revision, and any mandatory external
  Human Review evidence is present.
- **Rejected:** an authorized participant has rejected the commitment or
  supplied information with an explicit reason.
- **Disputed:** provider and consumer disagree; this records standing only and
  does not implement the Conflict Engine.
- **Superseded:** a separately identified successor commitment replaces this
  commitment for current use; historical reconstruction remains deferred.

The lifecycle is not task status, work progress, deliverable approval, Project
status, Workspace status, or Context authority.

Withdrawal is governed through the commitment's inherited current-use
relationship standing; it does not add a ninth Interface Commitment state or
rewrite the accepted state model. An authorized withdrawal:

- preserves the last Interface Commitment state and stable identity;
- removes the commitment from current operational reliance;
- requires an explicit reason and positive expected version;
- does not withdraw linked Context or sources;
- does not imply rejection, dispute, supersession, fulfilment, or consumer
  approval;
- remains traceable and may restore the same identity and retained state
  through an authorized, reasoned, version-protected action.

### Commitment Change Impact

An explicit indication that a provider, source, revision, required-information
definition, intended use, or related Context change may require consumer
reassessment.

This standing:

- must identify the triggering reference and reason;
- is recorded only by an authorized action;
- does not infer impact;
- does not automatically change Context authority or lifecycle;
- does not automatically create Missing Information, Conflict, task, review,
  notification, or decision records;
- remains visible until an authorized action addresses it.

### Relationship Audit Hook

The centralized audit integration point for material relationship and
commitment events.

Audit evidence must identify, as applicable:

- actor;
- action;
- relationship or commitment identity;
- governing Project;
- provider and consumer Workspace scope;
- relationship meaning;
- affected Context and source references;
- before and after standing;
- reason;
- resulting version;
- timestamp.

Audit evidence proves that an action occurred. It does not replace the
relationship, commitment, source, review, or engineering decision.

## Required Behaviors

### Explicit creation

- Create no relationship or Interface Commitment implicitly.
- Require an authenticated, active, authorized actor.
- Validate governing Project and every endpoint before creation.
- Require an allow-listed relationship meaning.
- Require explicit direction where meaning is directional.
- Require a bounded purpose or intended use.
- Reject missing, inaccessible, inconsistent, cross-Project, or unsupported
  endpoints.
- Reject accidental duplicate active relationship identity.
- Create one stable identity and initial positive version.
- Create success audit evidence atomically with successful creation.

### Relationship direction and semantics

- Preserve source and target roles.
- Prevent direction reversal from changing meaning silently.
- Prevent one meaning from being changed into another as an ordinary update.
- Require a new explicit relationship identity when engineering semantics
  materially change.
- Keep applies-to and evidenced-by references governed by PATCH-020.2.1.
- Prevent relationship access from becoming general graph traversal.

### Project and Workspace boundaries

- Require one governing Project for every relationship and commitment.
- Require every Workspace endpoint to belong to that Project.
- Keep shared Project Context singular at Project scope.
- Reference shared Context rather than copying it into provider or consumer
  Workspaces.
- Preserve Workspace-specific interpretation as separately attributable
  Context.
- Reject cross-Project relationships and commitments.
- Permit cross-Workspace relationships only when both Workspaces belong to the
  same Project and the actor has the required bounded capability.
- Preserve archived Workspace relationships and commitments without treating
  them as normal current operational dependencies.

### Relationship lifecycle

- Permit only explicit, authorized Current-to-Withdrawn and
  Withdrawn-to-Current changes.
- Require reason and expected version.
- Preserve identity and endpoints.
- Prevent ordinary physical deletion.
- Reject self-transition and stale-version mutation.
- Ensure failed lifecycle changes leave relationship and audit state
  unchanged.

### Interface Commitment creation

- Require one consuming Workspace.
- Require one valid provider representation.
- Require precise required-information meaning and stated use.
- Require semantic completeness and source expectations.
- Require a steward and consumer review responsibility.
- Require confidentiality and recorded criticality standing.
- Require a stage or due condition without creating scheduling behavior.
- Reject a provider or consumer outside the governing Project.
- Reject a commitment that makes the same Workspace silently fulfil both
  provider and consumer accountability without an explicit justified external
  or Project-level provider role.
- Record provider and consumer relationships explicitly.

### Interface Commitment lifecycle

- Permit only transitions consistent with the semantic ordering and
  accountable actor boundary.
- Provider acknowledgement must be an explicit provider-side action.
- Information Provided must identify the supplied source and revision and must
  meet the required-information qualification contract.
- Information Provided must not imply consumer acceptance.
- A provider must not mark consumer review complete.
- Consumer Review Required must remain distinct from fulfilment.
- Fulfilled for Stated Use must identify the bounded use, source, and revision.
- Fulfilment must be prohibited when EDS-020.2 requires Human Review and no
  separately governed review evidence exists.
- This patch must not create that Human Review evidence.
- Rejection, dispute, and supersession require explicit actor, reason, and
  expected version.
- Disputed standing must not select a winner or resolve engineering meaning.
- Superseded standing must not physically erase the earlier commitment.
- Commitment withdrawal and restoration must use the governed current-use
  standing without changing the retained Interface Commitment state.
- Withdrawal and restoration require an authorized actor, reason, and expected
  version and must preserve identity and prior state.
- Unsupported transitions and self-transitions must fail without mutation or
  success audit evidence.

The implementation plan must define and review the complete permitted and
prohibited transition matrix before implementation begins.

### Provider authority boundary

- Provider responsibility permits acknowledgement and delivery only within
  the provider’s authorized scope.
- Provider delivery does not change Context authority.
- Provider delivery does not approve consumer interpretation.
- Provider ownership does not prove competence.
- Provider access does not grant access to unrelated consumer Context.
- A provider may not alter consumer-owned Context or consumer review standing.

### Consumer authority boundary

- Consumer access is limited to the commitment and Context or source meaning
  separately authorized for the consumer.
- Consumer participation does not grant unrestricted provider Workspace
  access.
- Consumer response does not alter provider-owned source meaning.
- Consumer fulfilment action requires the applicable designated capability and
  any required external review evidence.
- Consumer ownership, assignment, collaboration, or recency does not
  automatically establish review authority or competence.

### Change and reassessment

- Permit an authorized actor to record explicit potential impact and
  reassessment-needed standing.
- Identify the triggering Context, source, revision, relationship, or
  commitment reference and reason.
- A material supplied-source revision must prevent silent continued
  fulfilment.
- Reassessment standing must be visible to authorized provider and consumer
  participants.
- Clearing reassessment standing must require an explicit, reasoned,
  version-protected action.
- No automatic impact inference, lifecycle transition, review, task,
  notification, Conflict, or Missing Information record may occur.

### Responsibility changes

- Require an active internal User for human stewardship or review
  responsibility.
- Validate the actor’s governance capability.
- Keep provider, consumer, information owner, steward, and reviewer
  responsibilities distinguishable.
- Require separate explicit, audited actions where changing multiple
  responsibilities would obscure accountability.
- Reject missing, inactive, unauthorized, or out-of-scope responsibility.
- Never infer competence or authority from ownership or assignment.

### Authorization and confidentiality

- Use only existing roles and participation foundations.
- Evaluate authorization before disclosure, totals, traversal, or mutation.
- Hide inaccessible relationship and commitment identifiers where disclosure
  would leak protected Context.
- Evaluate Project scope, Workspace scope, explicit responsibility, and source
  confidentiality independently.
- Apply least privilege to every connected Context and source.
- Relationship visibility must not grant transitive visibility.
- A consumer may view only provider meaning needed for the commitment and
  separately authorized by source restrictions.
- An administrator may administer but gains no technical authority or
  automatic access to separately restricted source meaning.
- Archived Workspace dependencies must not appear as current operational
  relationships.

### Optimistic concurrency

- Every material relationship or commitment mutation requires a positive
  expected version.
- Provider changes, consumer changes, fulfilment, and commitment withdrawal
  require the same positive expected-version protection.
- One successful mutation increments the version exactly once.
- A stale version produces a controlled conflict.
- Concurrent writers must not both succeed for the same prior version.
- Concurrency failure changes no lifecycle, responsibility, endpoint, supplied
  source, revision, reassessment standing, or audit state.
- Relationship concurrency must remain compatible with, but independent from,
  the versions of linked Context and Workspace objects.

### Audit and atomicity

Create centralized success audit evidence for:

- relationship creation;
- relationship metadata update;
- relationship withdrawal and restoration;
- relationship responsibility change;
- Interface Commitment creation;
- provider change;
- consumer change;
- provider acknowledgement;
- information provision;
- consumer-review-required standing;
- fulfilment for stated use;
- commitment withdrawal and restoration;
- rejection;
- dispute;
- supersession;
- responsibility change;
- criticality-standing change;
- source-relationship change;
- supplied-source or revision change;
- reassessment-needed recording and clearing.

Create no success audit evidence for:

- validation failure;
- authorization rejection;
- inaccessible endpoint or source;
- cross-Project or unauthorized cross-Workspace relationship;
- duplicate relationship identity;
- unsupported relationship meaning;
- unsupported lifecycle transition;
- missing required information qualification;
- provider or consumer authority violation;
- stale-version conflict;
- persistence failure;
- audit failure.

Relationship or commitment mutation and its success audit evidence must
complete in one transaction. Audit failure must roll back the domain mutation.

### Workspace compatibility

- Preserve one Workspace identity per Project and Discipline.
- Preserve Workspace owner, assignment, membership, status, archive, version,
  and audit behavior.
- Prevent a relationship or commitment from changing Workspace identity,
  Discipline, ownership, assignment, status, archive state, or version.
- Keep Context responsibility separate from Workspace responsibility.
- Preserve existing Project and Workspace behavior when no relationship or
  commitment exists.
- Preserve existing PATCH-020.2.1 behavior when no relationship or commitment
  exists.

### Safe failure

When authorization, scope, source, endpoint, responsibility, lifecycle,
version, or required meaning cannot be established safely:

- reject the action;
- avoid partial persistence;
- avoid false success audit evidence;
- avoid identifier, count, endpoint, source, or relationship leakage;
- avoid authority or competence inference;
- preserve the last valid state.

- provider responsibility does not grant consumer authority;
- consumer participation does not grant provider-source mutation;
- responsibility change requires valid active scope;
- source restriction can deny access despite relationship participation.

### Change and reassessment

Verify:

- explicit source or revision reference;
- material revision change prevents silent continued fulfilment;
- reassessment-needed standing is visible only to authorized participants;
- explicit version-protected clearing;
- no inferred impact;
- no automatic lifecycle change;
- no automatic Human Review, Missing Information, Conflict, task,
  notification, or decision creation.

### Optimistic concurrency

Validate:

- positive expected version;
- exactly one increment for one successful mutation;
- one winner and one controlled conflict under concurrent mutation;
- concurrent commitment transition;
- concurrent responsibility change;
- concurrent supplied-revision change;
- concurrent provider change where permitted;
- concurrent consumer change where permitted;
- stale commitment fulfilment;
- stale commitment withdrawal;
- stale conflicts leave relationship, commitment, source, reassessment, and
  audit state unchanged;
- linked Context and Workspace versions are not mutated.

### Audit and rollback

Verify complete success evidence for every material event required by this IDS.

Verify no success audit evidence for every rejected class identified under
Audit and Atomicity.

Force audit failure and persistence failure to prove:

- relationship creation rolls back;
- commitment creation rolls back;
- lifecycle change rolls back;
- responsibility change rolls back;
- supplied-information change rolls back;
- reassessment change rolls back.

Audit validation must explicitly cover successful relationship metadata
update, provider change, consumer change, commitment withdrawal and
restoration, criticality-standing change, and source-relationship change.

After every failure, compare domain state, version, endpoints, source
references, commitment state, and audit count with the pre-action baseline.
