# IDS-020.2.1: Core Context Foundation

## Status

Accepted

## Purpose

This Implementation Design Specification defines the bounded implementation
contract for PATCH-020.2.1, Core Context Foundation.

The patch establishes the minimum governed Engineering Context foundation
needed to associate traceable engineering meaning with an existing Project or
Engineering Workspace. It realizes only the first sub-patch authorized by
accepted EDS-020.2.

This IDS does not authorize implementation. Implementation may begin only
after this IDS is approved and an Implementation Readiness Review returns
**Ready for Implementation**.

## Scope

PATCH-020.2.1 is limited to:

- stable Context identity;
- explicit Project or Workspace scope;
- Context ownership and stewardship responsibility;
- the minimum authority-standing foundation;
- the minimum source-reference foundation;
- minimum relationships required to connect Context to its native subject,
  scope, and supporting source;
- bounded Context kinds assigned to this sub-patch;
- minimum lifecycle and concurrency behavior;
- authorization using existing Project and Workspace participation;
- baseline audit integration for material successful change;
- compatibility with PATCH-020.1 Workspace Core.

The allowed Context kinds are:

- Subject Reference;
- Qualified Fact;
- Qualified Engineering Value;
- Assumption;
- Source and Evidence Reference.

Project Context represents shared meaning once at Project scope. Workspace
Context represents discipline-bounded meaning within one existing Workspace.
Context refers to native Project, Workspace, Discipline, User, and engineering
subjects without taking ownership of their identity or lifecycle.

Minimum relationship meanings are limited to:

- a Context element applies to one or more identified native subjects;
- a Context element belongs to exactly one governing Project scope;
- a Workspace-scoped Context element identifies exactly one Workspace within
  that same Project;
- a Context element is supported by an identified source reference where
  source support is claimed.

These minimum links do not authorize the general relationship capability
assigned to PATCH-020.2.2.

## Explicit Non-Scope

PATCH-020.2.1 does not include:

- AI behavior;
- AI Insights;
- AI-generated Context;
- Derived Context;
- Missing Information detection or management;
- Conflict detection or management;
- Historical Context capability;
- snapshots;
- Context search;
- Engineering Decision Log capability;
- Engineering Execution Plan capability;
- Engineering Health or Workspace Readiness;
- Knowledge Graph capability;
- Interface Commitments;
- general Context relationship traversal;
- cross-Workspace provider and consumer relationships;
- source-precedence resolution;
- authority-promotion workflow;
- Human Review capability;
- formal engineering or deliverable approval;
- maturity progression;
- freshness evaluation or expiry policy;
- criticality assessment workflow;
- correction or supersession workflows;
- non-additive or unrelated persisted-state transition work;
- user-interface behavior;
- new roles or professional-competence certification;
- creation or ownership of Project, Workspace, Customer, Discipline, User,
  Document, Equipment, Tag, Standard, Vendor, Calculation, or Risk domains.

Later sub-patches may add only the capabilities assigned to them by accepted
EDS-020.2 and separately approved implementation contracts.

## Required Domain Objects

The names in this section describe required domain responsibilities. They do
not prescribe technical representation.

### Context Identity

A stable identity for one bounded Context element.

Required meaning:

- identity remains stable across authorized changes;
- identity is distinct from every native subject identity;
- identity does not create a universal Engineering Context Object;
- identity is unique within the governed Context boundary;
- identity is traceable in material audit evidence.

### Context Scope

The explicit boundary within which a Context element has meaning.

Required meaning:

- one governing Project;
- optional governing Workspace;
- applicable Discipline when Workspace-scoped;
- one or more identified native subjects;
- stated engineering purpose or applicability boundary where needed to avoid
  ambiguity.

A Workspace-scoped element must belong to the same Project as its Workspace.
Project-scoped shared meaning is not copied into each Workspace.

### Subject Reference

A governed reference connecting Context to a native subject.

Required meaning:

- native subject kind and stable identity;
- subject scope;
- relevance of the Context element to the subject;
- no transfer of native ownership or lifecycle authority.

The initial required subjects are Project, Workspace, and Discipline. Other
subject references are permitted only when a governed native identity already
exists and the reference remains inside the approved first-release subject
boundary.

### Qualified Fact

A source-supported claim about a subject for a bounded purpose and scope.

Required meaning:

- explicit claim;
- subject and scope;
- applicable source reference;
- authority standing;
- responsible owner and steward;
- current-use standing;
- uncertainty or qualification where material;
- concurrency basis.

A Qualified Fact is not authoritative merely because it exists.

### Qualified Engineering Value

A Qualified Fact whose engineering meaning requires a value and its
qualifications.

Required meaning, where applicable:

- value;
- unit;
- quantity meaning;
- tolerance or range;
- basis;
- reference, operating, or design condition;
- source and source standing;
- effective or observation time;
- uncertainty;
- subject and applicability scope.

Required qualifications may not be silently omitted when their absence would
change engineering meaning. Unsupported conversion, normalization, or
inference is prohibited.

### Assumption

An explicit provisional, human-owned basis used within a bounded scope.

Required meaning:

- assumption statement;
- accountable human owner;
- subject and scope;
- reason;
- known consequence or limitation;
- supporting source where one exists;
- current-use standing;
- condition requiring later confirmation, rejection, or withdrawal.

An Assumption must remain distinguishable from a fact and cannot be silently
promoted.

### Context Responsibility

Explicit accountability for maintenance and technical meaning.

Required meaning:

- information owner responsible for availability and controlled change;
- engineering steward responsible for technical meaning, applicability,
  completeness, and quality within an assigned scope;
- designation actor and time;
- active internal User requirement for the steward;
- Project or Workspace boundary of responsibility.

Ownership, assignment, collaboration, administration, and stewardship remain
independent. None proves professional competence.

### Authority Standing

The explicit bounded basis on which a Context element may or may not be relied
upon.

PATCH-020.2.1 supports only the standing needed by its allowed kinds:

- **Authoritative Fact:** supported by a governed source or process for the
  stated scope and use;
- **Engineer-Verified Fact:** existing verified standing supported by
  traceable authorized human evidence;
- **Assumption:** provisional human-owned basis.

This patch may preserve and expose valid standing but does not introduce Human
Review or authority-promotion workflows. Creation must never assign
Engineer-Verified standing without pre-existing qualifying evidence and
authorization. Administrator role, ownership, recency, repetition, confidence,
or source presence alone cannot establish or promote authority.

### Context Source Reference

A bounded provenance link to supporting evidence. It does not copy, replace,
approve, or take ownership of the native source.

Required meaning, where applicable:

- source kind;
- native source identity or stable reference;
- source owner;
- revision or issue;
- effective or observation time;
- issue or maturity standing supplied by the source;
- confidentiality or access restriction;
- applicability scope;
- known limitation.

This patch records provenance only. It does not resolve competing sources,
establish universal precedence, ingest documents, or interpret source content
automatically.

### Context Lifecycle Foundation

The minimum standing needed to distinguish Context available for current use
from Context withdrawn from current reliance.

Required meaning:

- initial current-use standing is explicit;
- withdrawal is an explicit authorized action with reason;
- a withdrawn element is excluded from normal current use;
- withdrawal does not imply that its source or native subject was deleted;
- every material change advances the concurrency basis;
- stale concurrent change is rejected without partial success.

Full correction, supersession, expiry, historical reconstruction, and snapshot
behavior remain outside this patch.

### Context Audit Hook

The connection between a successful material Context action and centralized
audit evidence.

Required meaning:

- actor;
- action;
- Context identity;
- Project and Workspace scope;
- affected subject;
- before and after meaning where material;
- reason;
- resulting concurrency basis;
- time;
- non-sensitive source reference where applicable.

Audit evidence records who did what and when. It does not replace Context
meaning or future historical capability.

## Required Behaviors

### Identity and scope

- Create each allowed Context kind with one stable identity.
- Require exactly one governing Project.
- Permit Workspace scope only for an existing Workspace in that Project.
- Preserve the Workspace’s governed Discipline.
- Reject missing, inconsistent, inaccessible, or cross-Project scope.
- Reject unsupported Context kinds.
- Prevent a Context identity from competing with a native subject identity.

### Project and Workspace ownership

- Keep shared Project meaning at Project scope.
- Keep discipline-local interpretation attributable to its Workspace.
- Reference shared Project Context rather than copying it into Workspaces.
- Preserve native Project and Workspace ownership and lifecycle.
- Prevent Context change from changing Project or Workspace status, ownership,
  assignment, collaboration, Discipline, or archival state.
- Prevent archived Workspace Context from appearing as current operational
  Context.

### Responsibility

- Require an authorized information owner.
- Require an explicitly designated active engineering steward for technical
  meaning.
- Constrain responsibility to Project or Workspace scope.
- Record every material owner or steward designation change.
- Reject inactive, missing, unauthorized, or out-of-scope designations.
- Do not infer stewardship, review authority, or competence from participation.

### Qualified meaning

- Require every fact, value, and assumption to identify its subject and scope.
- Require facts claiming source support to identify the source reference.
- Require engineering values to retain every qualification necessary for
  engineering meaning.
- Preserve Assumption as provisional and human-owned.
- Reject an element whose required qualification is missing, contradictory,
  or outside its subject scope.
- Do not invent a default value, unit, basis, condition, source, uncertainty,
  applicability, or authority.

### Authority foundation

- Make authority standing explicit and bounded to purpose and scope.
- Require traceable evidence and authorization for initial authoritative or
  pre-existing verified standing.
- Prevent one dimension from silently determining another.
- Reject hidden or unsupported authority promotion.
- Treat information without sufficient authority evidence as ineligible for
  authoritative standing.
- Preserve the distinction between ownership, stewardship, authorization,
  competence, and authority.

### Source foundation

- Link a Context element to its source without duplicating the source.
- Preserve native source identity, revision, scope, access limitation, and
  known limitations where applicable.
- Check source access before disclosure or change.
- Reject a source outside the governing Project or authorized external
  reference boundary.
- Preserve competing evidence without selecting a winner; conflict management
  remains deferred.
- Never treat source kind alone as universal precedence.

### Minimum relationships

- Support only applies-to, scoped-by, and evidenced-by meaning required by this
  patch.
- Preserve direction from Context to subject, governing scope, and source.
- Reject self-reference, cross-Project inconsistency, unsupported relationship
  meaning, and inaccessible targets.
- Never transfer ownership, authority, maturity, competence, or approval
  through a relationship.
- Do not expose unrestricted traversal through a permitted link.

### Lifecycle and concurrency

- Require a current concurrency basis for every material change.
- Advance the basis exactly once for each successful material change.
- Reject stale concurrent change atomically.
- Prevent rejected change from partially altering Context or its links.
- Require explicit reason and authorization for withdrawal.
- Exclude withdrawn Context from normal current-use behavior without presenting
  a historical capability.

### Authorization and confidentiality

- Use existing roles combined with Project ownership or assignment, Workspace
  ownership or assignment, collaborator membership, explicit information
  ownership, and stewardship.
- Permit contribution only within the actor’s authorized Project or Workspace
  scope.
- Apply source confidentiality independently from Context participation.
- Prevent unauthorized actors from learning restricted Context or source
  existence where that would disclose protected information.
- Treat administrator access as administrative, not technical competence.
- Fail safely when actor, scope, source, subject, or responsibility cannot be
  authorized.

### Audit

- Create centralized success audit evidence for creation, material value
  change, source-link change, owner change, steward change, authority-standing
  change, withdrawal, and restoration to current use where authorized.
- Keep non-sensitive before and after meaning when material.
- Create no success audit evidence for unauthorized, rejected,
  validation-failed, or concurrency-conflicted attempts.
- Ensure Context change and its success audit evidence complete together.
- Never use audit evidence as a substitute for domain meaning.

### Workspace Core compatibility

- Preserve one Workspace identity per Project and Discipline.
- Preserve derived Workspace naming.
- Preserve Workspace owner, optional primary assignee, collaborators,
  lifecycle, archival behavior, version behavior, permissions, and audit.
- Preserve Project ownership of Customer, Project lifecycle, Project owner,
  Project primary assignee, and the Workspace collection boundary.
- Prevent Context from becoming a nested Workspace or alternate Project.
- Preserve existing supported Workspace behavior when no Context exists.

### Safe failure

Rejected behavior must:

- identify the permitted limiting condition without leaking protected data;
- avoid unsupported defaults;
- avoid partial change;
- avoid authority promotion;
- avoid false success audit evidence;
- preserve the prior valid concurrency basis and Context meaning.

## Forbidden Behaviors

PATCH-020.2.1 explicitly prohibits:

- generic JSON Context or any undifferentiated Context blob;
- a universal Engineering Context Object that erases distinct semantics;
- duplicated Project, Workspace, Customer, Discipline, User, or native
  engineering-subject data;
- Context ownership of native Project or Workspace identity or lifecycle;
- hidden authority assignment or promotion;
- authority inferred from ownership, stewardship, assignment, collaboration,
  administrator role, source kind, recency, repetition, or confidence;
- implicit ownership being treated as engineering competence;
- AI creation, mutation, review, promotion, interpretation, or recommendation;
- unqualified engineering values;
- assumptions represented as facts;
- copied source content presented as a Context source of truth;
- silent source precedence or silent conflict resolution;
- relationship meaning beyond the minimum allowed scope;
- cross-Project Context links;
- unrestricted cross-Workspace traversal;
- archived Workspace Context represented as current operational Context;
- destructive removal as ordinary lifecycle behavior;
- partial success on invalid or concurrent change;
- success audit evidence for failed mutation;
- new roles, formal approval, or professional qualification claims;
- behavior belonging to PATCH-020.2.2 or any later sub-patch;
- implementation outside the approved PATCH, EDS, and IDS scope;
- hidden technical or architectural decisions.

## Definition of Done

PATCH-020.2.1 is complete only when:

- only allowed Context kinds exist;
- Context identity is stable and distinct from native subjects;
- every Context element has one valid Project scope;
- Workspace-scoped Context belongs to one Workspace in that Project;
- shared Project meaning is not duplicated into Workspaces;
- Project, Workspace, Discipline, and subject identities remain native;
- Qualified Facts preserve subject, scope, source support, standing, and
  responsibility;
- Qualified Engineering Values preserve all required engineering
  qualifications;
- Assumptions remain explicit, provisional, and human-owned;
- owner and active steward responsibilities are explicit and independently
  authorized;
- authority standing is explicit, evidence-based, and never promoted
  implicitly;
- source provenance and access limitations remain traceable without copying
  source ownership;
- minimum relationships are bounded, directional, and non-transferring;
- current-use and withdrawal behavior is explicit;
- concurrency rejects stale changes without partial success;
- successful material changes create complete centralized audit evidence;
- failed or rejected changes create no success audit evidence;
- existing Project and Workspace behavior remains compatible;
- authorization and confidentiality boundaries pass;
- no out-of-scope capability is represented as complete;
- additive database migration planning is complete where applicable;
- applicable migration rollback and recovery validation passes;
- direct PostgreSQL constraint validation passes for the approved integrity
  rules;
- focused validation, complete regression, and Final Review pass;
- working-tree hygiene and protected-environment checks pass;
- implementation evidence is ready for the governed Commit gate.

## Validation Requirements

Validation must use the existing isolated PATCH validation environment and
must not alter protected development data.

### Focused domain validation

Verify:

- creation of every allowed Context kind;
- rejection of every unsupported Context kind;
- stable identity and valid Project scope;
- valid Workspace scope and matching Project and Discipline;
- rejection of cross-Project or inaccessible subject links;
- Project Context reuse without Workspace duplication;
- qualified engineering values with required units, bases, ranges,
  tolerances, conditions, and uncertainty where applicable;
- rejection when a required engineering qualification is absent;
- explicit Assumption behavior distinct from fact behavior;
- source provenance, revision, applicability, and restriction preservation;
- minimum relationship allow-list and direction;
- withdrawal from current use;
- archived Workspace current-use exclusion;
- concurrency success and stale-change rejection.

### Responsibility and permission validation

Verify complete permitted and prohibited behavior for:

- administrator;
- Project owner;
- Project primary assignee;
- Workspace owner;
- Workspace primary assignee;
- Workspace collaborator;
- explicit information owner;
- designated engineering steward;
- unrelated engineer;
- inactive or missing responsible User.

Verify independently that:

- ownership does not imply competence;
- administrator role does not imply technical authority;
- contribution does not imply verification authority;
- source restriction can deny access despite Context participation;
- Project authority does not silently become Workspace stewardship;
- Workspace participation does not authorize shared Project applicability.

### Authority validation

Verify:

- explicit bounded authority standing;
- accepted initial standing with sufficient evidence and authorization;
- rejection of unsupported Authoritative Fact standing;
- rejection of unsupported Engineer-Verified standing;
- no promotion from ownership, role, recency, repetition, or confidence;
- Assumption cannot become fact through ordinary edit;
- authority standing remains independent from ownership and lifecycle.

### Audit and rollback validation

Verify successful audit evidence for every material event authorized by this
patch.

Verify no success audit evidence is created for:

- invalid identity or scope;
- unsupported Context kind;
- unauthorized actor;
- inaccessible source or subject;
- invalid owner or steward;
- missing engineering qualification;
- unsupported authority standing;
- prohibited relationship;
- stale concurrency basis;
- rejected lifecycle action;
- any partially attempted change.

For every rejected case, confirm the prior Context meaning, links, concurrency
basis, and audit state remain unchanged.

### Workspace compatibility validation

Verify:

- all PATCH-020.1 lifecycle and permission behavior remains unchanged;
- Workspace uniqueness remains unchanged;
- Workspace archival behavior remains unchanged;
- Context cannot change Workspace identity or status;
- Context absence does not change existing Project or Workspace behavior;
- existing Workspace audit behavior remains intact.

### Integrity and regression validation

Verify:

- additive database migration planning is complete where applicable;
- applicable forward migration behavior is deterministic;
- applicable migration rollback and recovery preserve protected data and the
  prior valid state;
- direct PostgreSQL constraint validation rejects invalid persisted states
  governed by the approved integrity rules;
- direct integrity rejection for invalid kind, invalid scope, invalid
  concurrency basis, invalid responsibility, unsupported relationship, and
  duplicate identity;
- focused PATCH-020.2.1 behavior passes;
- the complete backend regression suite passes;
- syntax and static integrity checks pass;
- document and source formatting checks pass;
- generated test and language cache artifacts are removed;
- development-data fingerprint remains unchanged;
- working-tree changes contain only approved PATCH files;
- staged content remains empty until explicit approval.

### Performance and security considerations

Before implementation begins, IRR must approve representative isolated data
and measurable targets for:

- bounded retrieval by Project, Workspace, and subject;
- deterministic bounded collections where this patch exposes collections;
- prevention of unbounded relationship traversal;
- authorization before disclosure;
- source-confidentiality enforcement;
- predictable concurrency behavior;
- audit completion without partial Context success.

Performance improvement must not weaken engineering meaning, authorization,
traceability, concurrency, or audit integrity.

### Required report
