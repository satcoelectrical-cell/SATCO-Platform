## Withdrawal-Semantics Result

**PASS**

Withdrawal is governed through the commitment's inherited current-use
relationship standing. It does not add another Interface Commitment state or
rewrite the accepted EDS state model.

The IDS now requires withdrawal to:

- preserve stable commitment identity;
- retain the last Interface Commitment state;
- remove the commitment from current operational reliance;
- require an authorized actor, explicit reason, and positive expected version;
- preserve linked Context and sources;
- remain distinct from rejection, dispute, supersession, fulfilment, and
  consumer approval;
- permit restoration of the same identity and retained state through a
  governed version-protected action.

Lifecycle and validation sections require withdrawal and restoration behavior,
permitted and prohibited transition coverage, failure atomicity, and audit
evidence. No workflow or Historical Context implementation is introduced.

## Concurrency Result

**PASS**

The optimistic-concurrency contract now explicitly covers:

- provider changes where permitted;
- consumer changes where permitted;
- commitment fulfilment;
- commitment withdrawal;
- relationship and commitment lifecycle transition;
- responsibility and supplied-revision change;
- stale mutation rejection.

Every material mutation requires a positive expected version. One successful
mutation increments once, concurrent writers cannot both succeed for the same
prior version, and stale failure leaves lifecycle, responsibility, endpoints,
source, revision, reassessment, and audit state unchanged.

Linked Context and Workspace versions remain independent.
