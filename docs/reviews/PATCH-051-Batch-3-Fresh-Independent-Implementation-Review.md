## Finding register

### MAJ-051-B3-01 — Project configuration removal is unusable on PostgreSQL

`DisciplinePackageConfigurationService._remove_project_once()` applies
`FOR UPDATE` to `SELECT count(*)` at
`backend/app/services/discipline_package_configuration_service.py:177`.
PostgreSQL rejects that query, so the required valid `CONFIGURED →
NOT_CONFIGURED` removal flow cannot run even when there are zero bound
Workspaces.  This violates the accepted Project state/removal semantics.

**Minimum implementation remediation:** lock the candidate bound Workspaces in
the accepted ascending-ID order (or otherwise use a legal lock-preserving
existence query), then perform the zero-bound check; add an isolated PostgreSQL
test for both successful removal and bound-Workspace rejection.

### MAJ-051-B3-02 — Compatibility validation is not exact provenance matching

The configuration validation at
`discipline_package_configuration_service.py:205-211` and Workspace binding
validation at `discipline_package_service.py:168-171` filter compatibility
rows only by `package_key` and count the filtered rows.  They neither compare
`CompatibilityMember.package_version`/`descriptor_digest` with the requested
exact selections nor prove that the selected set is the complete combination.
A selected subset of a larger allowed combination, or a different executable
version of the same key, can therefore be accepted.  The code also bypasses
the accepted Batch-1 deterministic compatibility evaluator.

This is a material violation of ADR-024/EDS-051 exact PackageKey/version/
profile/Registry provenance and the no-fuzzy/no-implicit-resolution rule.

**Minimum implementation remediation:** evaluate the full ordered exact
selection tuples through the Batch-1 deterministic compatibility engine (or
an equivalent exact persisted representation), including package key, version,
descriptor digest and complete combination cardinality.  Apply the same result
to Project configuration and Workspace applicability/rebind, with PostgreSQL
vectors for subset, wrong-version, wrong-digest and exact-match cases.

### MAJ-051-B3-03 — M3 does not meet the accepted cutover algorithm or prove it

Implementation-Plan-051 requires M3 to lock scope, process ascending-ID
chunks, verify counts/checksums and validate M2 objects.  M3 instead performs
six unrestricted value-wide updates at
`e05100000003_workspace_binding_cutover.py:48-54`; it contains no scope lock,
chunking, count/checksum comparison or M2-object validation.  The migration
tests are static source assertions only.

Further, the test bootstrap creates a PASS artifact without `alembic_head`
(`tests/conftest.py:35-40`), while M3 requires exactly
`e05100000002` (`e05100000003_workspace_binding_cutover.py:106`).  A fresh
test database upgrade to M3 would fail this gate; the reviewed database was
already at M3.  The reported 91-test run therefore cannot demonstrate a fresh
M3 upgrade/backfill/trigger/recovery path.

**Minimum implementation remediation:** implement the accepted bounded M3
cutover algorithm and add real isolated PostgreSQL upgrade tests using a
digest-valid, matching M2 preflight artifact.  Cover six-value backfill,
unknown/null/duplicate refusal, counts/checksums, deferred trigger rejection,
and forward-only recovery.

### MAJ-051-B3-04 — Required two-session concurrency and retry evidence is absent

The accepted plan explicitly requires two independent PostgreSQL
Sessions/barriers for revocation-first and mutation-first schedules,
membership/role/Organization changes, retry-after-revocation, Workspace
creation, Project rebind/owner transfer and Organization configuration races.
`test_discipline_package_transaction.py` contains only guard constants,
shared/shared coexistence and two manually constructed UoWs.  It never invokes
a guarded configuration or Workspace retry loop after a retryable failure and
contains no authority/resource race.  `test_discipline_package_service.py`
uses a factory bound to the fixture connection rather than two independent
business-operation sessions, and covers only success/stale DTO scenarios.

As a result, revocation-wins, mutation-wins, fresh retry revalidation,
lock-retention through commit, multi-Workspace ordered locking and atomic
rebind rollback are not acceptance-proven on real PostgreSQL.

**Minimum implementation remediation:** add the accepted independent-session
barrier matrix and use it to prove both serial schedules, fresh Session/
connection/guard reacquisition on each retry, no success Audit/protected write
after revocation-first, and complete rollback of a forced rebind failure.
